# Printing and PDF export

## Status

The AoS 4 cutover deleted the whole print/PDF feature. It has been rebuilt against AoS 4 in
`src/aos4/print/` — see [The current implementation](#the-current-implementation) below.

The AoS 3 code was **not** restored: it depended on `types/army`, `ducks`, `utils/reminderUtils` and
other retired modules, and AGENTS.md forbids reviving them. What survived is its *behaviour*, which
the rest of this document records so the rebuild had something to match.

The legacy source is still readable on `master` (commit `d585a0a7`):

```sh
git show origin/master:src/utils/pdf/generate/layouts/layoutUtils.ts
```

Paths in the next two sections are `origin/master` paths. Everything from
[The current implementation](#the-current-implementation) onwards is this branch.

## Two independent printing paths

The app has always had two unrelated ways to get an army onto paper.

### 1. Browser print (CSS only)

`Ctrl+P` on the reminders page. There is no dedicated print view — the live DOM is restyled by
Bootstrap 4 print utilities plus a small `@media print` block.

| Piece | Location | Role |
| --- | --- | --- |
| `@media print` overrides | `src/css/index.scss:271-320` | Forces white-on-dark text to black, shrinks headers/cards, widens `.ReminderContainer` to 90% |
| `.PageBreak` | `src/css/index.scss:272-275` | `page-break-inside: avoid` — applied to reminder cards |
| `PrintArmy` | `src/components/print/printArmy.tsx` | `d-none d-print-block` army-selections header, print-only |
| `PrintFooter` | `src/components/print/printFooter.tsx` | `d-none d-print-block` "Generated by AoS Reminders" footer |
| `d-print-none` | toolbar, header, banners, notes, donate, footer | Hides interactive chrome from print |

Both print components are lazily loaded in `src/components/routes/Home.tsx:69-71`. `PrintArmy`
duplicates the selections rendering with its own hand-rolled 70-character line wrapper
(`getWrappedItemText`, commented "Here be dragons").

This path is low-effort and low-fidelity. It is not what the Download button uses.

### 2. PDF export (jsPDF)

The "Download PDF" button in the toolbar. This is the hand-written code with all the magic numbers.

```
toolbar.tsx
  └─ components/print/pdfButton.tsx          (lazy)
       ├─ useGetReminders()                  → IReminder  (phase → TTurnAction[])
       ├─ selectors.selectCurrentArmy        → ICurrentArmy (faction + selections)
       ├─ selectors.selectReminders          → hiddenReminders: string[]
       ├─ selectors.selectNotes              → INote[]
       └─ savePdf({ ...currentArmy, hiddenReminders, reminders, notes })
            └─ utils/pdf/generate/generatePdf.ts
                 ├─ saveDefaultPdf(data)  → jsPDF   ("Standard" layout)
                 └─ saveCompactPdf(data)  → jsPDF   ("Compact" layout)
                      ↓
            components/modals/download_pdf_modal.tsx
                 └─ pdf[layout].save(`${fileName}.pdf`)
```

Notable: **both** PDFs are built eagerly on button click, before the user has chosen a layout. The
modal only picks which pre-built `jsPDF` instance to `.save()`. On a large army this does twice the
work, and it happens synchronously on the main thread.

The button also calls `saveArmyToS3(currentArmy)` as a side effect, and the modal fires
`logDownloadEvent(factionName, layout)` analytics on save.

## Library

`jspdf@1.5.3`, pinned. That is a 2019 release and several majors behind (jsPDF 3.x). The code uses
1.x-only APIs that were removed in 2.x:

- `doc.setFontStyle(style)` → replaced by `setFont(family, style)`
- `doc.text(text, x, y, null, null, align)` → replaced by `text(text, x, y, { align })`

Any upgrade is a rewrite of the render loops, not a version bump. Per AGENTS.md this belongs in
Phase 2.

The document is created with `new jsPDF({ unit: 'in', lineHeight: 1.2 })` — **inches**, and the
default format, which is **A4**: 8.2678in × 11.6929in. Not US Letter, despite the audience.

## Architecture: two passes

`CompactPdfLayout` (`utils/pdf/generate/layouts/layoutUtils.ts`, exported as default and used by
*both* layouts — the class name is a leftover) does measurement and pagination. The per-layout files
do the actual drawing.

**Pass 1 — build a flat list of styled lines.** `getReminderText(reminders, notes)` walks the
reminder phases and turns each rule into `ICompactPdfTextObj[]`:

```ts
interface ICompactPdfTextObj {
  type: 'army' | 'armyEnd' | 'armyFooter' | 'armyName' | 'break' | 'desc'
      | 'note' | 'phase' | 'spacer' | 'title' | 'titlespacer'
  text: string
  position: 'col' | 'full' | 'col0' | 'col1'
}
```

Every string is pre-wrapped here with `doc.splitTextToSize()`, so from this point on one object is
exactly one rendered line. Reminders are filtered by `getVisibleReminders()` and reordered by
`reorderReminders()` (which honours the user's drag-and-drop order from `LocalReminderOrder`) before
this runs.

**Pass 2 — pack lines into pages.** `splitTextToPages()` returns `ICompactPdfTextObj[][]`, one array
per page. Vertical fit is decided purely from `Styles[type].spacing`, accumulated into `_pageY` and
compared against `_opts.pageBottom`. `_getRuleHeight` / `_getRulesHeight` sum spacings so a whole rule
can be kept together.

**Pass 3 — draw.** `compact.ts` / `default.ts` iterate the pages and call `doc.text()`, replaying the
same spacing arithmetic to recover Y. Decorations are emitted inline: a rounded rect around each
`phase`, a rule above `armyName` and below `armyEnd`, the page number and `aosreminders.com` watermark
plus small logo on `i === 0`, and a full-size logo after the last line if it fits.

The two files are ~90% identical. Only `Styles`, `PageOpts`, the `col1X` column and the `colY`
bookkeeping differ.

## Styles and page options

`TPdfStyles` maps each `type` to `{ fontSize, spacing, style, textColor? }`. `spacing` is the line
advance **in inches** — it is not derived from `fontSize`, it was tuned by hand per layout.

`IPageOpts` (`layoutUtils.ts:15-25`) carries the six wrap widths plus `pageBottom`, `xMargin`,
`yMargin`.

| Option | Standard | Compact |
| --- | --- | --- |
| `xMargin` / `yMargin` | 0.5 / 0.75 | 0.3 / 0.75 |
| `pageBottom` | `12.4 - 0.75` = 11.65 | 9 |
| `maxLineWidth` | 10.8 | 17 |
| `maxTitleLineWidth` | 8.8 | 15 |
| `maxNoteLineWidth` | 8.8 | 16.5 |
| `colLineWidth` | 0 (unused) | 8.5 |
| `colTitleLineWidth` | 0 (unused) | 8 |
| `colNoteLineWidth` | 0 (unused) | 8 |
| second column X | — | 4.2 |

Note `pageBottom` in Compact is 9, well short of the 11.69in A4 height — Compact leaves ~2.7in of
dead space at the bottom of every page. Standard's 11.65 is correct for A4.

## The magic numbers: why `maxLineWidth` is 17 on an 8.27in page

This is the single most confusing thing in the file and the reason tuning it felt like trial and
error. The wrap widths are **not inches**, even though everything else in the document is.

`splitTextToSize(text, maxlen)` in jsPDF 1.5.3 does
(`node_modules/jspdf/dist/jspdf.debug.js:14155`):

```js
var fontUnit_maxLen = 1.0 * this.internal.scaleFactor * maxlen / fsize
//  fsize = options.fontSize || this.internal.getFontSize()
```

so `maxlen` is in document units (inches) **at the font size that is active when you call it**.

All the `splitTextToSize` calls happen in pass 1 — `getReminderText`, `_getArmyText`, `_fullToCol` —
and pass 1 runs *before* the render loop, which is the only place `setFontSize()` is ever called. So
at split time the document is still at **jsPDF's default font size of 16pt**, regardless of the size
the line will eventually be drawn at.

The result is a hidden scale factor:

```
rendered width (in) = maxlen × renderFontSize / 16
```

Every wrap constant in both layouts is therefore `desired_inches × 16 / fontSize`. Verified against
jsPDF's own `getTextWidth()`:

| Constant | Value | Rendered at | Actual width | Space available | |
| --- | --- | --- | --- | --- | --- |
| Standard `maxLineWidth` (desc) | 10.8 | 9.5pt | 6.33in | 7.27in | ok |
| Standard `maxTitleLineWidth` | 8.8 | 10pt | 5.45in | 7.27in | ok |
| Standard `maxLineWidth` (army) | 10.8 | **11pt** | **7.33in** | 7.27in | **overflows** |
| Compact `maxLineWidth` (desc) | 17 | 7pt | 7.37in | 7.67in | ok |
| Compact `colLineWidth` | 8.5 | 7pt | 3.55in | 3.90in | ok |
| Compact `colTitleLineWidth` | 8 | 7pt | 3.47in | 3.90in | ok |
| Compact `maxLineWidth` (army) | 17 | 6pt | 6.31in | 7.67in | ok |

The one failure falls out of the table immediately: the army-selections block reuses `maxLineWidth`,
which was tuned for the 9.5pt `desc` style, but `army` renders at 11pt. Long selection lines eat
about 0.16in into the 0.5in right margin. It stays on the paper, so nobody has reported it.

**Any change to a `fontSize` silently changes every wrap width that style uses.** That is the trap.

## Compact column packing

`_addPhaseToPages_Compact` (`layoutUtils.ts:104-225`) is the hardest code in the feature. Per phase:

1. If the phase has an odd number of rules, the last one is popped off to be rendered full-width.
   If it was the *only* rule, it is emitted full-width and the phase is done.
2. Compute `halfHeight` = half the total height of the remaining rules; fill `col0` until it reaches
   `halfHeight`, then switch to `col1`.
3. Whenever a rule would overrun `pageBottom`, either divert it to `col1` or start a new page with a
   `"<Phase> (continued)"` header and reset both column heights.
4. The popped full-width rule is shoehorned into `col1` via `_fullToCol()` (re-wrapping it to column
   width) if it fits under `col0`'s height; otherwise it is drawn full-width, on a new page if needed.

Y bookkeeping is split across the two passes and does not agree. In pass 1, `_addToCurrentPage`
deliberately **skips advancing `_pageY` for `col1` lines** (`layoutUtils.ts:67`) so both columns
measure against the same Y. In pass 2, `compact.ts:164-170` keeps a separate `colY`, advances
whichever column the line belongs to, and resyncs `y = colY` when `col1` runs past `col0`. The two
models drift, which is why the overrun checks in pass 1 are written as deltas
(`this._willOverrunY(col1H - col0H + ruleHeight)`) rather than absolute positions.

There is no test coverage for any of this. The PDF fixtures under `src/tests/fixtures/*/pdf/` are
*import* fixtures for the Azyr and Warscroll Builder parsers — nothing exercises generation.

## Known rough edges

Ordered roughly by how much they hurt.

1. **Hidden 16pt wrap-width unit.** Documented above. Every width constant is coupled to a font size
   through an invisible factor.
2. **Two hand-maintained copies of the render loop.** `compact.ts` and `default.ts` diverge only in
   constants but must be edited in lockstep; the phase rect uses `setLineWidth(0.0001)` in one and
   `0.00055` in the other, and the rect Y fudge differs (`+0.04`/`+0.015` vs `+0.02`/`+0.08`).
3. **Spacing is duplicated across passes.** Pagination sums `style.spacing`; rendering re-adds it.
   Any divergence is a silent layout bug.
4. **Both PDFs generated on every click**, synchronously, before the layout is chosen.
5. **A4 hardcoded**, no Letter option, and the Compact layout wastes 2.7in per page from
   `pageBottom: 9`.
6. **Army block overflows the right margin** in the Standard layout (table above).
7. **Manual line advance instead of jsPDF's own text layout.** `lineHeight: 1.2` is passed to the
   constructor and then ignored, since every line is placed individually.
8. **Notes are faked with `'     '` prefixes** (`layoutUtils.ts:324`) instead of an indent.
9. **jsPDF 1.5.3** is five years stale and uses removed APIs.
10. **No tests, no golden files.** Every change is verified by eyeballing a downloaded PDF.

## The current implementation

Two approaches were built and compared: a planned PDF, and a dedicated print view driven by a CSS
print stylesheet. **The planned PDF won and is what ships.** The CSS print view was removed; see
[Why not the CSS print view](#why-not-the-css-print-view) for what it gave up.

```
Aos4ReminderViewModel[] + army summary
        │
        └─ createAos4PrintDocument()      src/aos4/print/document.ts
              → PrintDocument             sections → rules → labelled paragraphs
                    │
        └─ planPrintLayout()              src/aos4/print/layout.ts
              → PrintPlan                 positioned lines, pure
                    │
        └─ renderPrintPlanToPdf()         src/aos4/print/pdf.ts
              → jsPDF                     drawn, saved from the toolbar modal
```

`PrintDocument` is presentation-neutral: no jsPDF, no DOM, no React. Keeping it separate from the
layout is what makes the layout testable and would make a second renderer cheap if one is ever wanted.

### Modules (`src/aos4/print/`)

| File | Role |
| --- | --- |
| `types.ts` | `PrintDocument`, `PrintPreset`, `PlacedLine`, `PrintTextMeasurer` |
| `document.ts` | Reminders → `PrintDocument` |
| `presets.ts` | `STANDARD_PRESET`, `COMPACT_PRESET`, `withPageSize()` |
| `measure.ts` | jsPDF-backed text measurement, in real inches |
| `layout.ts` | `planPrintLayout()` — wrapping, keep-together, pagination, column balancing |
| `pdf.ts` | `renderPrintPlanToPdf()` — draws a plan, makes no layout decisions |

What changed from the legacy version:

- **Layout is a plan, not a side effect.** `planPrintLayout()` is pure and returns positioned lines.
  Tests assert on geometry directly instead of parsing a PDF, and the renderer is a thin adapter.
- **Presets are data.** `compact.ts` and `default.ts` collapsed into two entries in `presets.ts`.
  Adding a layout is a table entry, not a third copy of a render loop.
- **`spacing` is derived** from `sizePt × leading` rather than hand-tuned alongside the font size.
- **Widths are inches.** `measure.ts` sets the font size *before* measuring, so the 16pt scale factor
  documented above is gone. A wrap width of `3.5` means three and a half inches.
- **Page size is a parameter.** `withPageSize(preset, 'letter')` — A4 and US Letter both work.
- **Rules never split.** A rule moves to the next column or page whole. It is only broken when it
  cannot fit in an otherwise empty column, and the continuation is titled `… (continued)`.
- **Section headings repeat** with `(continued)` at the top of any column or page they spill into,
  and never strand themselves at the foot of a column.
- **Columns are balanced** on the trailing page by binary-searching the shortest column height that
  still fits the same pages without breaking an extra rule. Full pages balance themselves.

### Why not the CSS print view

The rejected alternative was a print-only DOM (`components/print/printView.tsx` + `css/print.scss`)
rendered from the same `PrintDocument`, using `@page` for the sheet, `break-inside: avoid` to keep a
rule whole, and `column-count: 2` for the compact layout. It was simpler — a component and a
stylesheet, no measurement or pagination code — and it got real hyphenation and orphan/widow control
for free.

It lost on control:

- **No `(continued)` headings.** CSS cannot repeat a section heading when a section spans a page.
  This is structural, not a gap in the implementation.
- **No page numbers, and no file.** Output goes through the browser's print dialog, where margins,
  scaling, and the browser's own headers and footers are the user's to override.
- **Pagination varies by browser.** Chrome, Firefox, and Safari break differently, so the result is
  not reproducible.

If it is ever wanted back, it was `printView.tsx` and `print.scss` in PR #1722, and it read
the same `PrintDocument` that ships today.

### Using it

The toolbar's **Download PDF** button opens a modal with layout (Standard/Compact), page size
(A4/Letter), and a file name.

Plain browser printing (`Ctrl+P`) still works against the live app DOM, using the pre-existing
`@media print` rules and `d-print-none` classes in `css/index.scss`. It is not a designed print
path — the PDF is.

### Tests

| File | Covers |
| --- | --- |
| `src/tests/aos4/printDocument.test.ts` | Hidden reminders, grouping, ordering, paragraphs, summary |
| `src/tests/aos4/printLayout.test.ts` | Margins, column containment, keep-together, continuations, text preservation, balancing, Letter |
| `src/tests/aos4/printPdfRenderer.test.ts` | The PDF actually matches the plan, page count, nothing off-page |

The layout suite runs against both presets and asserts *properties* rather than golden files, so it
fails on a real overflow rather than on an intentional style tweak. The regression guard for the 16pt
trap is `wraps to the real column width, not to an implicit font-size-scaled width`.

## Still open

- **The logo.** The legacy PDFs embedded a base64 logo on every page and a full-size one on the last
  page if it fitted. The current PDF has the `aosreminders.com` watermark and page numbers, but no
  logo.
- **jsPDF is current (#1900).** `pdf.ts` and `measure.ts` run on `jspdf` 4.x — `setFont(family,
  weight)` and the options-object `text()` signature. The official-PDF side of the same upgrade
  (`pdfjs-dist` 6 in `data/gamesWorkshop/pdfText.ts`) extracts slightly different text than 2.4 did
  (letterspaced display headings no longer gain fake spaces), so the accepted corpus's pinned
  official-evidence checksums need a reviewed refresh before `data:aos4:generate:candidate` passes
  again.
- **A layout-engine library not taken.** `pdfmake` or `@react-pdf/renderer` would express "two
  columns, keep-together, repeat heading on break" as configuration rather than code. Rejected
  against AGENTS.md's "avoid dependency churn during Phase 1", but it is the natural landing spot if
  `layout.ts` keeps growing.
